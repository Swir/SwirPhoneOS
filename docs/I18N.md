# Global localization architecture

SwirPhoneOS is designed for worldwide use from the start. Localization is a platform contract rather than a collection of hard-coded per-screen strings.

## Current host implementation

`swirphoneos/locales/catalogs.json` is the data source for the desktop/runtime localization layer. `swirphoneos/i18n.py` validates it before use.

The current Flash Studio catalog contains English, Polish, Norwegian Bokmal, German, Spanish, French, Portuguese and Arabic. English is the canonical fallback. Arabic is explicitly marked RTL. This catalog coverage applies only to the currently implemented desktop strings; it must not be interpreted as completed translation of the future mobile OS.

The validator enforces:

- one canonical English source catalog;
- BCP-47-style locale normalization with region fallback;
- English fallback for unsupported locales or missing translated keys;
- duplicate-key rejection;
- bounded string/key data;
- placeholder parity between source and translations;
- explicit `ltr` / `rtl` direction metadata;
- machine-readable translation coverage via `python -m swirphoneos i18n`.

Adding a translated catalog is data-only; Python application logic does not need to change.

## Mobile system contract

The Android/AOSP product must reuse the same principles while mapping them to Android resource qualifiers and framework locale APIs. The first-boot experience, lock screen, launcher, SystemUI, Settings, recovery/update surfaces, SwirRoot and every bundled first-party app must obtain user-visible text from localized resources rather than application logic.

Required platform behavior:

- detect the best device/user locale during setup;
- fall back to English when the requested translation is unavailable;
- support language + script + region tags rather than assuming a two-letter language is always sufficient;
- use locale-specific date, time, number and unit formatting;
- use the system time zone unless the user explicitly changes it;
- support plural rules rather than string concatenation;
- support font/script fallback and appropriate input methods;
- mirror layouts and navigation where RTL languages require it;
- allow text expansion without clipping controls;
- keep accessibility labels localized with visible UI strings;
- keep translation coverage measurable and testable.

## Translation quality gates

A locale is not called complete merely because it exists in a registry. Before a locale can be presented as fully supported for a release candidate, CI/review should verify at least:

1. no missing required strings for the release scope;
2. placeholder/plural compatibility;
3. no accidental hard-coded user-facing English in the covered components;
4. basic layout review at increased font size;
5. RTL layout review for RTL locales;
6. first-boot, Settings, recovery/update and critical-error-path coverage;
7. native-speaker or qualified translation review where practical.

Translation progress is separate from the global weighted engineering percentage in `project.json`; localization metadata alone does not complete the `swir_ux` milestone.
